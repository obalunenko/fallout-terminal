## Summary

The Overseer gets three private play operations next to `ResetFacilityDevice`: run one authored transition, force a device into any state, and switch one fault on or off. Each one follows the reset path exactly: a facility-wide revision check, one atomic durable commit, an audit record, withdrawal of a pending player request, and reprojection to player terminals. A card transition reuses `resolveWorldTransitions`, so it applies the same source-state, precondition, and fault-effect rules as a player command. It does not touch command state.

The control service keeps a bounded, in-memory feed of the last five changes per device. The feed is projected through the existing coordination-state event, so no new event name is needed. A device reset that changes only faults currently fails the App and JS result checks; this plan fixes those checks. The Overseer «Объекты» detail area is reordered: the device header comes first, then the play card, then actions grouped by role, then tabs. The scenario guide follows a rule plus a choice remembered for the run, and its sticky step bar goes away. Session JSON does not change.

## Call Paths

The companion block templates are missing in this install (`plan-blocks.py` cannot find its parts), so these blocks are written by hand.

| Path | Steps |
|---|---|
| Card transition | `overseer.js` card button → `desktopAPI.applyFacilityDeviceTransition` → `App.ApplyFacilityDeviceTransition` (lock, proto round trip, trim checks) → `control.Service.ApplyFacilityDeviceTransition` (commit closure: revision check, store call, result check, audit, withdraw pending, reproject, feed entry) → `session.Service.ApplyFacilityDeviceTransition` (`resolveWorldTransitions`, one commit) → App validator → publish session state and coordination state → `onSessionState` / `onCoordinationState` → re-render |
| Forced change, fault switch | Same layering with `ForceFacilityDeviceState` and `SetFacilityConditionActive`; the session op sets one value instead of resolving a transition |
| Device reset | Unchanged path; App and JS validators accept a fault-only result; control adds the withdrawal audit and a feed entry |
| Player command applied or refused | Existing control paths in `service.go` (approval, decline, failure, capability block) also append feed entries for every device in the command's authored action |
| Session opened | `App` → `control.ReplaceFacility` clears the feed with the rest of the runtime facility state |

## Constitution Check

| Principle | Assessment |
|---|---|
| I. Accepted desktop runtime | PASS. Wails v3 private bridge only. No runtime change. |
| II. Protobuf source of truth | PASS. Three request messages and the feed are protobuf-defined. Results reuse `FacilityOperationResult`. |
| III. Server-authoritative state | PASS. Every play change is a unary request checked against the facility revision. The card's precondition verdict is display-only and the server decides. Updates arrive through the existing events. |
| IV. Public/private separation | PASS. All three operations and the feed are private desktop and coordination contracts. The public player service still never accepts a raw transition. |
| V. Safe schema evolution | PASS. Additive messages and field 11. Feed variants use `oneof`. New enums start at `UNSPECIFIED`. Buf breaking runs against the baseline. |
| VI. Session JSON version 1 | PASS. No new session fields. Play changes write the existing `currentStateId` and `currentActive`. The feed is runtime-only. |
| VII. Complete cutovers | PASS. The rename field and its «ГОТОВО» / «ОТМЕНА» are removed with their tests. `RecoverFacilityCondition` stays because it still serves terminal-scoped faults. |
| VIII. Player activity observable | PASS. Withdrawn requests are now logged on device reset as well as scene reset. Logs carry IDs only. The feed is never built from logs. A logging failure leaves outcomes unchanged. |
| IX. Demo sessions | PASS. The reactor gains «Критический перегрев» for forced change, and every new path is listed in `sessions/demo-capability-paths.md`. |
| Testing and quality gates | PASS. Go table tests, race tests, Buf, bindings check, browser test per story, `go fix ./...` before commit. |
| Development workflow, step 1 (branch from `develop`) | Justified violation; see Complexity Tracking. |
