# Bug Report: Legacy Transition Prevents Moving Its Target Into the Source Group

**Type**: Untested flow
**Severity**: High

**Reported**: 2026-08-25
**Status**: Patched
**Patched**: 2026-08-25

**Implemented**: 2026-08-25

## Description

An older version-1 session has no persisted `terminalGroups` data and contains an authored terminal transition from terminal A to terminal B. On open, compatibility normalization correctly represents A and B through separate deterministic singleton groups, leaving the old transition authored but dormant.

The Overseer then attempts the intended repair: move terminal B into terminal A's singleton group. After the destructive change is reviewed and confirmed, the complete group replacement is rejected instead of coupling the endpoints. For the reported session, command `adm-emergency` in terminal `t-krel-admin` targets `t-krel-emergency`, and the application returns:

```text
terminal group candidate invalidates authored transitions: terminal transition command "adm-emergency" in terminal "t-krel-admin" targets terminal "t-krel-emergency" and crosses groups "singleton-7cd1dc224dc802a75a131c9b" and "singleton-e422e66e867ded2106b9b34c"
```

The group IDs in the rejection are the separate singleton groups visible before the proposed move. The confirmed candidate should instead place both endpoints in terminal A's group, remove terminal B's now-empty singleton group atomically, preserve the command, and make the authored transition eligible. The rejection therefore evaluates or transports a grouping state that does not reflect the reviewed move. No partial mutation is reported, but the required legacy-session coupling workflow is blocked.

### Reproduction

1. Open a legacy session that has terminals A and B, no persisted groups, and an authored transition A -> B.
2. Verify that open-time normalization presents A and B in separate singleton groups and preserves the transition command.
3. From terminal B's contextual actions, choose the move operation and select terminal A's singleton group as the destination.
4. Review and confirm the destructive group change.
5. Observe that replacement is rejected as though A and B still crossed their original singleton groups.

**Expected**: B moves exactly once into A's group, B's empty source group is removed, the transition remains authored, and A -> B becomes a valid same-group transition.

**Actual**: The operation is rejected with the pre-move singleton group IDs and the canonical groups remain unchanged.

## Root Cause Analysis

The feature decomposed legacy compatibility, terminal movement, and authored-link safety into separate test cases. Domain coverage proves that a legacy cross-singleton link is dormant and that replacing both singleton groups with a newly created coupled group can validate. Move coverage uses sessions without authored transitions, while browser legacy coverage stops after proving that the dormant command cannot execute. No completed task exercises the user's positive repair variant: retain terminal A's normalized singleton identity, move target B into that existing group, remove B's singleton, and carry that exact candidate across the production UI and private mutation boundaries.

The implementation trace found that the current production path already preserves the complete reviewed candidate: the Overseer move draft removes B from every group, removes B's empty singleton, appends B to A's retained singleton, and the private route, coordinator, session service, and domain validator preserve and evaluate that exact candidate. Focused production-service regressions pass the reported repair and still reject candidates that genuinely leave transition endpoints cross-group. The reported stale-singleton rejection is therefore not reproducible against the current production source.

The first failing controlled boundary was the browser fixture: after persisting the accepted grouping candidate, it retained its pre-move navigation catalog, so the repaired command incorrectly remained dormant. The fixture now refreshes that catalog from the accepted canonical session. The primary process cause remains the missing cross-scenario regression, which allowed stale integration projections—and potentially older application builds—to escape detection.
