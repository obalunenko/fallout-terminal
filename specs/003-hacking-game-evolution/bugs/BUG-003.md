## Description

The production player flow still violates the forced-success reconciliation contract introduced by
BUG-002. A player selects an incorrect password on the hacking screen. The Overseer then presses the
private **Hack successful** control. The player briefly sees
`ДЕЙСТВИЕ ОТКЛОНЕНО: invalid-action`; the terminal transitions back to its menu while the same notice
remains visible, and the notice disappears only after its transient display lifetime expires.

**Observed reproduction**:

1. Open an active password-hacking puzzle as a player.
2. Select an incorrect candidate password.
3. In the Overseer application, press **Hack successful**.
4. Observe the raw `invalid-action` rejection appear and survive the hacking-to-menu transition.

**Expected**: The successful trusted solve remains the only player-facing outcome. No rejection from
the superseded hacking interaction appears on the hacking surface or follows the player into the
terminal menu.

**Actual**: The trusted solve succeeds and navigation returns to the terminal menu, but a raw rejection
notice is rendered across both surfaces before eventually disappearing.

**Evidence**: `/Users/olegbalunenko/Desktop/Screenshot 2026-08-28 at 05.05.42.png` shows the terminal
menu after the transition with `ДЕЙСТВИЕ ОТКЛОНЕНО: invalid-action` still visible. This reproduction
supersedes the automated-only verification recorded in BUG-002.

## Root Cause Analysis

BUG-002 correctly added an authoritative-outcome rule to the specification, but the implementation and
verification did not cover the production sequence now reproduced by the user. The player client still
renders the raw notice from `applyActionResult` when a rejected shared or presentation result matches a
pending request. The solved-state reconciliation is conditional on observing an unsolved-to-solved
transition with a non-empty matching hacking presentation context. The screenshot proves that, in the
real Overseer flow, a rejected result can still pass those guards or remain outside the context that is
cleared and reach the generic `invalid-action` notice path.

The precise production ordering or context mismatch has not yet been instrumented, so it would be
premature to attribute the failure to one transport channel. The confirmed process cause is a
verification blind spot: BUG-002 was closed using fixture-driven browser journeys while its own report
recorded that the post-fix native GUI replay was not performed. Those fixtures exercise delayed unary,
streamed-presentation, and shared-action cases, but they do not establish equivalence with the actual
private Overseer button path and its production snapshot ordering.
