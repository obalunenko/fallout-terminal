# Bug Report: Tagged Packages Do Not Carry the Release Version

**Type**: Spec conflict
**Severity**: High
**Feature**: 023-v2-release-preparation
**Reported**: 2026-08-27
**Status**: Patched
**Patched**: 2026-08-27
**Remediated**: 2026-08-27 — Constitution 8.1.0 and post-analysis artifact decisions applied

## Description

The governed release tag is validated as the release identity, but that version is not propagated
into the platform packages or the Go executable. A v2 tag can therefore publish artifacts that
still advertise version 1.0.0 or expose no authoritative application version at all:

- `build/darwin/Info.plist` hard-codes `CFBundleShortVersionString` and `CFBundleVersion` as
  `1.0.0`.
- `build/windows/info.json` hard-codes file and product versions as `1.0.0.0`.
- `build/windows/app.manifest` hard-codes the assembly identity as `1.0.0.0`.
- `internal/buildtool/buildtool.go` compiles with `-buildvcs=false` and linker flags that only strip
  symbols (plus the Windows GUI flag); it injects no application version.
- `.github/workflows/wails-portable.yml` validates `GITHUB_REF_NAME` in preflight, but the package
  jobs do not pass one canonical `VERSION` derived from that tag into the package entrypoint.
- Release archive inspection checks names, non-empty executables, and required resources, but not
  whether packaged platform metadata and executable version output agree with the release tag.

As a result, successful tag validation proves only the GitHub Release name. It does not prove the
identity of the binaries published under that name.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 1 — Publish a Valid V2 Release (P1), especially the promise
  that tagged source and release identity agree before packaging and publication.
- **Affected requirements**:
  - **FR-001** requires the governed application source identity to correspond to major version 2
    before a v2 release is tagged.
  - **FR-002** and **FR-003** govern release-tag validation, but do not require the accepted value
    to become a package/build input.
  - **FR-005** requires every active application package to resolve through the v2 identity, but
    does not require platform or executable version metadata to expose that identity.
  - **Impacted Application Surfaces — Build and packaging** identifies `build/`, `scripts/`, and
    release preflight as affected surfaces.
  - **Packaging/release verification** and **SC-001** verify tag acceptance/rejection only; neither
    checks artifact-version equality.
- **Gap identified**: The specification has no requirement, acceptance scenario, or success
  criterion establishing one canonical version from the validated tag, carrying it through every
  target build, generating platform-valid metadata from it, embedding it in the Go executable, and
  verifying the packaged result. More directly, the **Out of Scope** section explicitly excludes
  "Embedding the application release version in platform metadata or the running executable."
  That exclusion conflicts with the newly reported requirement that published artifacts identify
  themselves as the release version.

## Root Cause Analysis

The portable release implementation was designed around archive availability: preflight validates
the tag, while per-target eligibility validates only compilation, archive shape, executable
presence, and required resources. The accepted tag never crosses into the package process. The
build tool consequently copies static metadata templates and deliberately disables Go VCS metadata
without supplying an application version of its own. The current v2 release-preparation spec then
preserves that separation by placing runtime and platform version embedding out of scope, so a
normal plan and task generation pass cannot close the discrepancy.

This is classified as a spec conflict because the requested release invariant directly contradicts
the feature's explicit scope boundary. The hard-coded and absent metadata are the resulting
implementation manifestation.
