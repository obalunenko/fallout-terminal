# Bug Report: Authenticated ngrok Player Stalls Before Initial Snapshot

**Type**: Implementation drift
**Severity**: High
**Feature**: 005-connectrpc-protobuf-migration
**Reported**: 2026-08-13
**Status**: Patched
**Patched**: 2026-08-13
**Resolution**: Verified 2026-08-13

## Description

When ngrok mode is enabled and a player opens the authenticated public player
URL, the static player shell loads but the generated Connect subscription does
not deliver its initial snapshot. The connection overlay remains visible with
`УСТАНОВКА СВЯЗИ...`, and the player never sees the current transmitted terminal
presentation.

The visible string is the initial state set before `Subscribe` yields its first
message. Remaining on that overlay therefore indicates that public ngrok access
does not complete the required server-streaming handshake and snapshot path,
even though the page itself is reachable.

## Root Cause Analysis

The transport-level cause was reproduced and isolated. With an ngrok
traffic-policy file attached, a non-empty Connect server-streaming POST reached
the application but its response was held until client cancellation. The same
five-byte generated request frame streamed immediately through the local
listener and an otherwise identical ngrok tunnel without traffic-policy
processing. A non-matching policy rule still retained the failure, ruling out a
path-expression workaround. Host and Origin were preserved, unary requests
succeeded, and the application emitted HTTP `200` plus
`application/connect+proto`, ruling those candidates out.

The artifact-level root cause is clear: the authenticated-ngrok acceptance gate
was replaced by component simulations. `tests/browser/connectrpc-player.spec.mjs`
tests the protected prefix with static GET and unary `SoundManifest` requests,
while successful subscription, reconnect, and terminal-render journeys run on
the local fixture origin. `soak.md` and `validation.md` explicitly defer literal
public-ngrok observation but still record SC-030 and SC-031 as passing. This left
the actual public server-streaming path untested and allowed the implementation
drift to ship.

## Resolution

- Removed the ngrok traffic-policy file from the forwarding process and kept
  credentials out of ngrok process arguments.
- Added constant-time, fail-closed Basic Auth in the player application for
  every request whose Host exactly matches the configured public domain. Local
  and LAN hosts remain unchallenged, and same-origin validation is unchanged.
- Added protected-boundary and credential-gated actual-ngrok browser journeys,
  including first snapshot, overlay dismissal, terminal rendering, master-side
  stream update, fail-closed `401`, and reconnect.
- Replaced SC-030/SC-031 evidence and added SC-035. Schema checks, Go normal and
  race suites, frontend/player builds, 17 local browser journeys, two actual
  public-domain journeys, macOS packaging, runtime smoke, and hygiene checks
  pass. No affected criterion remains failed or `NOT RUN`.
