# Bug Report: Ordinary command rejection skips the access-error screen

**Type**: Spec gap
**Severity**: Medium
**Feature**: `010-terminal-navigation`
**Reported**: 2026-08-28
**Status**: Implemented
**Patched**: 2026-08-28
**Implemented**: 2026-08-28

## Description

When the controlling player selects an ordinary command and the Overseer
rejects that pending action, every player view is returned directly to the
unchanged source menu. The rejected request should instead use the existing
full-screen command rejection presentation and render the exact established
copy `Ошибка доступа`, as an initial state-changing command already does.

The rejection must remain effect-free: it must not reveal the ordinary
command's authored result, write durable command state, change terminal or
route state, or alter the saved source-menu navigation. The controller should
acknowledge the rejection through the same existing command-rejection flow
before all player views return to that menu. Overseer close-as-reject and an
explicit reject decision must have the same result.

This report is owned by `010-terminal-navigation`, where BUG-005 introduced
the behavior-independent approval gate and deliberately retained
mode-specific rejection presentations. The active
`028-interactive-approval-notifications` feature consumes the same trusted
decision path and requires notification decisions to match in-app decisions;
it does not define the underlying player rejection presentation. Terminal
transition and terminal-return rejection behavior is not changed by this bug.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 1 — «Перейти по команде в другой
  терминал», especially Acceptance Scenarios 8 and 9. Scenario 8 already puts
  ordinary commands in the same server-authoritative approval lifecycle as
  state-changing and transition commands, while Scenario 9 leaves the
  post-decision presentation mode-specific without requiring player-visible
  rejection feedback for an ordinary command.
- **Affected requirements**:
  - **FR-033** requires every ordinary, state-changing, completed, or
    transition command to enter one approval gate before any effect.
  - **FR-034** gives every pending command mode one shared full-screen record
    presentation, but defines no corresponding shared rejection presentation.
  - **FR-036** explicitly encodes the reported defect: initial state-change
    rejection shows `Ошибка доступа`, while ordinary rejection returns to the
    previous menu without a result.
- **Affected success criterion**: **SC-014** verifies the existing
  mode-specific rejection/acknowledgement presentation across all command
  modes and therefore currently accepts direct menu restoration for an
  ordinary rejection.
- **Gap identified**: The specification mandates universal approval but does
  not require visible rejection feedback for an ordinary command. It instead
  preserves the older direct-menu outcome in FR-036. The requested behavior
  must be specified before changing the implementation, so this is a spec gap
  rather than implementation drift.

- **Impact**: The plan must route an ordinary reject or close-as-reject to the

  observers, and reconnecting players, and retain the existing acknowledgement

## Root Cause Analysis

BUG-005 generalized command selection into one approval lifecycle but
deliberately preserved each mode's older post-decision presentation. That
decision was written into FR-036, the implementation plan, T042–T044, and the
cross-mode tests. The implementation therefore matches the current artifacts.

In `ResolveCommandExecution`, a rejected initial state-changing request stores
`CommandExecutionPhaseRejected`, while every other command-execution mode
clears `terminal.CommandExecution`. The ordinary-command test explicitly
requires that cleared presentation and unchanged navigation. Because the
player client already renders `Ошибка доступа` whenever it receives a rejected
command-execution presentation, the missing behavior is not a separate
frontend renderer; it is the intentionally omitted authoritative rejection
state for ordinary commands, backed by a specification that requires the old
menu restoration.
