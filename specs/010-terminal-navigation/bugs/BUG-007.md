# Bug Report: Terminal-transition rejection skips the access-error screen

**Type**: Spec gap
**Severity**: Medium
**Feature**: `010-terminal-navigation`
**Reported**: 2026-08-28
**Status**: Patched
**Patched**: 2026-08-28

## Description

When the controlling player selects a command that transitions to another
terminal and the Overseer rejects the request, every player view returns
directly to the unchanged source menu. Rejecting or closing that decision
should instead show the same server-authoritative full-screen rejection
presentation used by other rejected command types, with the exact text
`Ошибка доступа`.

The rejection must remain effect-free: it must not activate the target
terminal, push a route point, change either terminal checkpoint, alter the
source navigation, or write durable state. Controller, observers, and a
reconnecting player should retain the rejection presentation until the
controller acknowledges it through the established `Back` or `Enter` flow;
after acknowledgement, all players should return to the unchanged source
menu.

This report covers a forward terminal-transition command. The existing
terminal-return rejection behavior is not changed. Explicit reject,
close-as-reject, and the interactive approval-notification reject action must
continue to share the same trusted Overseer decision outcome rather than
introducing notification-specific player behavior.

## Root Cause Analysis

Terminal transitions intentionally use `PendingTerminalNavigation`, separate
from `PendingCommandExecution`. `ResolveTerminalNavigation` currently handles
reject by clearing the pending navigation and notice, after which the public
projection contains no pending or rejected transition state and the player
renders the unchanged source menu. The focused browser regression explicitly
asserts this immediate restoration.

BUG-006 added the access-error acknowledgement lifecycle only to ordinary
commands by retaining `CommandExecutionPhaseRejected`; it explicitly kept
terminal-transition rejection unchanged in the specification, plan, tasks,
and regression guards. The implementation therefore matches the current
artifacts. The new expected player feedback is a missing requirement and
design state, not implementation drift.
