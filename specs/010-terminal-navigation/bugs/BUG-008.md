# Bug Report: Completed state-changing rejection skips the access-error screen

**Type**: Spec gap
**Severity**: Medium
**Feature**: `010-terminal-navigation`
**Reported**: 2026-08-28
**Status**: Patched
**Patched**: 2026-08-28

## Description

After a state-changing command has already completed, the command remains
selectable in the player menu under its completed name. A repeated selection
correctly enters the shared Overseer approval flow without executing or saving
the state change again. However, when the Overseer rejects that request or
closes the decision dialog, all player views are returned immediately to the
unchanged source menu.

The completed state-changing command should use the same server-authoritative
rejection presentation as the other forward command modes: controller,
observers, and a reconnecting player should see the full-screen command record
with the exact text `Ошибка доступа` until the controller acknowledges it with
`Back` or `Enter`. Only then should every player return to the unchanged source
menu.

The rejection must remain effect-free. It must not reveal the frozen completed
result, execute or persist the state change again, alter the saved command
state, change terminal or route state, or mutate the canonical source-menu
navigation. Explicit reject, close-as-reject, and interactive approval
notification rejection must share the same authoritative outcome.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 1 — «Перейти по команде в другой
  терминал», especially Acceptance Scenarios 8 and 9. Scenario 8 already
  includes completed state-changing commands in the universal approval and
  full-screen pending lifecycle. Scenario 9 explicitly excludes only completed
  state-changing rejection from the common `Ошибка доступа` presentation.
- **Affected edge case**: The documented repeated selection of a completed
  state-changing command requires the same approval and waiting screen as any
  command, but does not define consistent visible feedback when that repeated
  request is rejected.
- **Affected requirements**:
  - **FR-028** and **FR-033** supersede the earlier approval-free completed
    repeat behavior and require every completed command selection to create an
    exact pending Overseer request before showing its frozen result.
  - **FR-034** requires the common full-screen pending surface for every
    command mode.
  - **FR-035** requires completed-command requests to be resolvable through the
    same private approve/reject/close boundary.
  - **FR-036** explicitly preserves the reported defect by requiring common
    rejection presentation for ordinary, initial state-changing, and forward
    terminal-transition commands while retaining the previous presentation
    only for completed state-changing rejection.
  - **FR-037** and **FR-038** define authoritative rejection, reconnect, and
    acknowledgement lifecycles for ordinary and forward-transition commands,
    but no equivalent requirement covers completed state-changing commands.
- **Affected success criteria**: **SC-013** covers completed-command pending
  convergence, while **SC-014** accepts the existing mode-specific rejection
  outcome. **SC-015** and **SC-016** prove the desired access-error lifecycle
  only for ordinary and forward-transition commands. There is no measurable
  criterion for a rejected completed state-changing command.
- **Gap identified**: The specification intentionally retained immediate menu
  restoration for the completed mode while progressively unifying ordinary
  and transition rejection behavior. The newly requested completed-command
  behavior is therefore missing from the normative artifacts rather than
  incorrectly implemented from an existing requirement.

## Root Cause Analysis

BUG-005 put ordinary, initial state-changing, completed state-changing, and
terminal-transition commands behind one approval boundary but deliberately
retained their earlier post-decision presentations. BUG-006 unified ordinary
rejection with the existing initial state-changing access-error flow, and
BUG-007 did the same for forward terminal transitions. Both fixes explicitly
kept completed state-changing rejection unchanged, leaving it as the only
forward command mode that restores the menu immediately.

The implementation matches those artifacts. `ResolveCommandExecution`
publishes `CommandExecutionPhaseRejected` only when the pending mode is
ordinary or initial state-changing; the completed branch clears
`terminal.CommandExecution`. `TestOrdinaryAndCompletedCommandDecisionsPreserveModeSpecificEffects`
expects that cleared presentation, and the completed branch of the Playwright
command-mode matrix expects the source menu immediately after reject/close.
The player already renders the required `Ошибка доступа` surface and supports
reconnect plus controller acknowledgement whenever it receives a rejected
command presentation. The missing behavior is the authoritative completed-mode
rejection state and its corresponding artifact/test requirements.
