# Bug Report: Rejection acknowledgement returns to the previous terminal and survives re-entry

**Type**: Implementation drift
**Severity**: High
**Feature**: `010-terminal-navigation`
**Reported**: 2026-09-03
**Status**: Patched
**Patched**: 2026-09-03
**Implemented**: 2026-09-03
**Verified**: 2026-09-03

## Description

Using `sessions/demo.json`, the player can enter protected terminal `t_demo2`
from `t_demo1`, complete the hacking puzzle, and select the ordinary command
`n_cmd_security_summary` (`Запросить сводку безопасности`). When the Overseer
rejects that command, the player correctly receives the full-screen `Ошибка
доступа` presentation, but the visible acknowledgement control is incorrectly
rendered as the route action `[ НАЗАД В Терминал смотрителя — Убежище 76 ]`.

Activating that control does not acknowledge the rejected command and restore
the `t_demo2` root menu. Instead, it creates a terminal-return request and,
after Overseer approval, navigates the player back to `t_demo1`. The rejected
command presentation remains stored in the suspended `t_demo2` runtime. When
the player selects `Подключиться к службе безопасности` again and the Overseer
approves the forward transition, `t_demo2` is reactivated with the old `Ошибка
доступа` screen instead of its initial/root menu. The player can only request
another return to `t_demo1`.

Expected behavior:

1. A rejected ordinary command on `t_demo2` shows only the ordinary
   controller acknowledgement semantics: `Back` or `Enter` clears the exact
   rejected presentation and restores the unchanged `t_demo2` menu.
2. That acknowledgement does not create a terminal-return request, change the
   active terminal, or mutate the route.
3. Once the rejection is acknowledged, the root route-return control may be
   used in a separate action.
4. Any later approved re-entry into the already hacked `t_demo2` opens its
   root menu without another hack and without a stale command rejection.

## Root Cause Analysis

The defect is caused by three existing implementation paths composing in the
wrong order:

1. `frontend/client/client.js` renders the rejected command through
   `renderCommandRecordSurface`, but that helper does not remove the
   `terminal-return` class or reset the back-button text left by the preceding
   root-list render. The access-error screen therefore advertises the route
   return instead of a command acknowledgement.
2. `internal/control.Service.DispatchPlayerAction` evaluates
   `rootReturnRequested` before dispatching the action to the live runtime.
   Because rejected presentation is detached from `Nav`, the terminal still
   satisfies root-list return conditions. A `Navigate back` sent to acknowledge
   `REJECTED` is intercepted as a new terminal-return request before
   `internal/live.Service` can clear `CommandExecution`.
3. After that unintended return suspends `t_demo2`, a later approved forward
   transition reuses `ReactivateRuntime`. Reactivation preserves the terminal
   checkpoint and revalidates navigation but does not clear the still-present
   rejected command presentation. `ResolveTerminalNavigation` resets the
   destination `Nav` to root but likewise leaves `targetRuntime.CommandExecution`
   intact, so the old rejection is published on re-entry.

Existing tests cover ordinary rejection acknowledgement, terminal return, and
solved-terminal reactivation separately. They do not cover their interaction
when the rejected ordinary command is selected at the root of a terminal with
a non-empty return route, allowing this implementation drift to pass all
marked-complete gates.
