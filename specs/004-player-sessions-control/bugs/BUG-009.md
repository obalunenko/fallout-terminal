# Bug Report: Controller Presentation Requests Flash a False Locked State

> **SUPERSEDED LEGACY PLAYER TRANSPORT — HISTORICAL, NON-AUTHORITATIVE.**
> The affected player boundary is the generated ConnectRPC `SetPresentation`
> path introduced by BUG-008; this report does not restore or modify the legacy
> handwritten WebSocket protocol. The current public-player contract is
> `specs/005-connectrpc-protobuf-migration/contracts/public-player.md`.

**Type**: Implementation drift
**Severity**: Medium
**Feature**: `004-player-sessions-control` — Player Sessions, Character Assignment, and Shared Terminal Control
**Reported**: 2026-08-21
**Status**: Patched
**Patched**: 2026-08-21

## Description

When the active controller moves between terminal menu rows with the pointer or
keyboard, every movement sends the authoritative generated ConnectRPC
`SetPresentation` request. While that request is pending, the terminal controls
briefly become grey/desaturated and the pointer changes from the normal action
cursor to the locked/not-allowed cursor. The normal appearance returns when the
authoritative presentation result is applied.

The controller is not actually read-only during this interval: BUG-008 permits
subsequent controller presentation movements and uses latest-wins request/result
handling. The transient visual lock therefore misrepresents the current role and
interaction authority, produces visible flicker on ordinary cursor movement, and
makes responsive menu navigation feel as if control is repeatedly lost and
restored.

Expected behavior: an active controller moving semantic selection remains
visually active and responsive while `SetPresentation` is in flight. The client
must still avoid optimistic selection and apply the highlight only from the
authoritative projection, but presentation-only pending state must not reuse the
grey/locked treatment reserved for genuinely blocked shared gameplay input or
observers.

## Root Cause Analysis

The first failing boundary is the player client presentation state, not the
coordinator or generated contract:

1. `beginControllerPresentation()` stores a new `pendingPresentationAction` and
   immediately calls `renderPlayerContext()` before sending `SetPresentation`.
2. `renderPlayerContext()` toggles `.shared-input-pending` whenever either
   `pendingSharedAction` **or** `pendingPresentationAction` is non-null.
3. `client.css` applies `cursor: not-allowed`, `opacity: .72`, and
   `filter: saturate(.55)` to terminal targets under `.shared-input-pending`.
4. The controller presentation gate intentionally does not reject a new movement
   merely because an earlier presentation request is pending; newer movement may
   supersede it. The CSS therefore claims the controls are locked while the
   JavaScript authority model says they remain actionable.

BUG-008 correctly made selection authoritative and non-optimistic, but reused the
older blocking gameplay pending presentation for a high-frequency, non-blocking
semantic movement request. Existing tests verified request ordering, observer
inertness, convergence, and eventual pending clearance, not the controller's
visual state during the request interval.
