# Bug Report: Rapid Hacking Hover Replays Stale Presentation

> **SUPERSEDED LEGACY PLAYER TRANSPORT — HISTORICAL, NON-AUTHORITATIVE.**
> The affected player boundary is the generated ConnectRPC `SetPresentation`
> path introduced by BUG-008; this report does not restore or modify the legacy
> handwritten WebSocket protocol. The current public-player contract is
> `specs/005-connectrpc-protobuf-migration/contracts/public-player.md`.

**Type**: Implementation drift
**Severity**: Medium
**Feature**: `004-player-sessions-control` — Player Sessions, Character Assignment, and Shared Terminal Control
**Reported**: 2026-08-21
**Status**: Patched
**Patched**: 2026-08-21

## Description

On the password-hacking screen, rapid pointer movement by the active controller
across symbol, password, and pattern targets sends a generated ConnectRPC
`SetPresentation` request for each distinct hovered target. The authoritative
presentation updates then arrive and render in their committed order after the
pointer has already moved elsewhere. As a result, the selected-target animation
and preview cue replay the cursor's earlier path, visibly lag behind the pointer,
and show the target currently under the pointer only after the pointer stops or
moves slowly enough for the request stream to catch up.

Expected behavior: rapid controller hover remains authoritative and shared, but
superseded intermediate hover targets must not build an unbounded presentation
backlog or replay stale selected-target feedback. The latest eligible semantic
target must converge promptly on all assigned views. Repeated movement within
one target must remain deduplicated, and observer input must remain inert.

## Root Cause Analysis

The first failing boundary is the player client's high-frequency presentation
dispatch policy:

1. Every hacking-cell `mouseover` calls `previewHackCell()`, which calls
   `beginControllerPresentation()` for the hovered semantic target.
2. `beginControllerPresentation()` rejects only a target equal to the currently
   applied authoritative presentation or the one stored in the latest local
   `pendingPresentationAction`; every other target creates and immediately sends
   another `SetPresentation` request.
3. Assigning a new `pendingPresentationAction` replaces local result-correlation
   state, but it neither cancels nor coalesces earlier requests already in flight.
4. The coordinator correctly commits those valid requests in order and publishes
   each presentation revision. `applyLiveTerminal()` then applies each accepted
   projection, invokes `playControllerPresentationCue()`, and renders the hacking
   preview even when the pointer has since advanced to a newer target.
5. Existing BUG-009 tests prove that two delayed movements remain dispatchable
   and do not look locked; they do not traverse enough hacking targets to expose
   request buildup, trailing authoritative highlights, or repeated preview
   animation/audio.

The generated contract and coordinator are behaving according to the requests
they receive. The drift is that client-side "latest-wins" currently means only
"track the latest result" rather than "bound high-frequency dispatch to the
latest semantic intent."
