# Bug Report: v2.0.0 Rejects the v2.1.0 Package Inventory

**Type**: Spec gap
**Severity**: High
**Feature**: 024-application-self-update
**Reported**: 2026-08-29
**Status**: Patched
**Patched**: 2026-08-29

## Description

A packaged macOS ARM64 installation of v2.0.0 discovers v2.1.0, downloads the complete
`Fallout-Terminal-darwin-arm64.zip` asset, and verifies its GitHub SHA-256 digest. Preparation then
fails before an adjacent replacement bundle is staged. The Overseer sees `Unable to prepare the
application update.` and the installed v2.0.0 application remains unchanged.

The published v2.1.0 archive added `RUNNING.md` to the schema-v2 manifest and payload. The v2.0.0
staging implementation requires the manifest, extracted inventory, and its compiled-in six-file
macOS inventory to have equal lengths. The seven-file v2.1.0 payload therefore fails with
`artifact manifest inventory does not match the extracted package` even though its archive digest,
manifest identity, file modes, and per-file digests are valid.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 2 — Apply a Trusted Update.
- **Affected requirements**: FR-011, FR-021, FR-022, and FR-024.
- **Affected success criteria**: SC-006 and SC-009.
- **Gap identified**: The specification requires a compatible replacement layout and a complete
  update path, but it does not require each newly published package inventory to remain consumable
  by the oldest supported release that can discover it. It also does not require a release-to-release
  acceptance test using that published updater binary or a recovery plan for a conflicting cohort.

### plan.md

- **Affected sections**: Implementation Steps 4 and 7, Testing Strategy, and Cutover and Rollback.
- **Impact**: Exact inventory validation was tested only with the builder and updater from the same
  source revision. The plan must add an explicit predecessor-consumer compatibility gate before a
  release is published and define how user-facing launch documentation can evolve without changing
  the self-update payload accepted by an already published strict validator.

### tasks.md

- **Affected tasks**: T022, T023, T025, T026, T039, and T044.
- **False completions**: These tasks correctly covered same-revision package validation, but their
  completion did not establish compatibility between the v2.0.0 updater and a later package shape.
- **Missing tasks**: Add a regression fixture or test that validates the next governed archive with
  the oldest supported published updater contract; restore a forward-fix inventory
  accepted by v2.0.0; and record a real v2.0.0-to-forward-fix macOS update/relaunch journey.

## Root Cause Analysis

Commit `32f5f88` added `RUNNING.md` to both package generation and the current staging allowlist.
That made same-revision tests pass while changing schema-v2 inventory without changing the schema
version. The already published v2.0.0 binary cannot learn the new allowlist and correctly fails
closed on the extra file. The release process checked the new archive with the new code, but did not
exercise the archive through the v2.0.0 consumer.

The published Darwin asset confirms the mismatch:

- release: `v2.1.0`, source revision `2c9c95fb5637840c72e6ed9f482f5272faac19eb`;
- archive SHA-256: `bd2769ee733f522627be30698d95e941e042aa55b83ef0f3af02266b839f980b`;
- v2.1.0 manifest inventory: seven regular payload files, including `RUNNING.md`;
- v2.0.0 macOS allowlist: six regular payload files, excluding `RUNNING.md`.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to encode predecessor-package compatibility in the specification,
   release contract, plan, and tasks.
2. Produce a higher strict-v2 forward-fix release; do not move the v2.1.0 tag or replace its assets.
3. Keep the forward-fix archive payload at the v2.0.0 schema-v2 inventory, and distribute
   `RUNNING.md` outside the governed five-asset release inventory until an intentional package
   schema migration can be supported.
4. Add cross-version regression coverage that feeds each proposed archive to the oldest supported
   staging contract, then verify a real v2.0.0-to-forward-fix Darwin ARM64 update.
5. Document that a manually installed v2.1.0 has the conflicting seven-file contract and requires
   one manual replacement to reach the forward-fix line.
6. Run `/speckit.bugfix.verify` before implementation and publication.
