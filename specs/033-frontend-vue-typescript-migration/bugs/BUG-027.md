# Bug Report: Newer public-access state leaves a completed settings dialog open

**Type**: Implementation drift
**Severity**: High
**Feature**: 033-frontend-vue-typescript-migration
**Reported**: 2026-08-31
**Status**: Patched
**Patched**: 2026-08-31

## Description

The production-root public-access parity test delivers a newer authoritative event while a settings save is pending, then resolves that save with an older successful snapshot. The canonical newer state is retained, but the dialog reports a stale error and stays open instead of treating the successful command as complete, clearing transient secrets, closing, and restoring focus.

## Artifact Traceability

### spec.md

- **Affected user story**: User Story 2 — Overseer migration.
- **Affected requirements**: FR-015, FR-022, FR-027, FR-050.
- **Gap identified**: Ordered snapshot suppression was implemented, but the dialog completion path did not preserve the established close/focus lifecycle when a newer event had already won.

### plan.md

- **Affected sections**: Wave e public-access integration and final parity.
- **Impact**: A successful stale command result must not replace newer state, but it must still complete the dialog lifecycle.

### tasks.md

- **Affected task**: T093.
- **False completions**: None; earlier focused checks did not expose this production-root ordering path.
- **Missing scope**: T093 must correct `PublicAccessSettingsDialog.vue` and rerun the retained suite.

## Root Cause Analysis

The dialog used the same branch for a failed stale command and a successful command whose snapshot merely lost to a newer event. That conflated canonical-state ordering with command lifecycle completion.

## Recommended Fix

1. Keep the newer authoritative snapshot and never dispatch the older result snapshot.
2. When the stale result is successful, close the dialog and restore focus after clearing transient state.
3. Retain the retry error only for an unsuccessful stale result.
4. Rerun public-access and complete T093 parity.
