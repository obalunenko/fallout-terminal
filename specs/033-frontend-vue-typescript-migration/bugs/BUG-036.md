# Bug Report: Native reset probe omits completed-command approval

**Type**: Untested flow
**Severity**: High
**Feature**: 033-frontend-vue-typescript-migration
**Reported**: 2026-08-31
**Status**: Patched
**Patched**: 2026-08-31

## Description

The real packaged T106 reset journey reaches two connected Players and displays the fixture's
frozen completed command names, but it times out after the controller selects one of those rows.
The Player correctly changes to the pending command surface because completed state-changing
commands retain the universal Overseer approval boundary. The native smoke never synchronizes with
or approves the packaged Vue `CommandExecutionDialog`, so it cannot reach the frozen result that it
requires before exercising reset.

## Root Cause Analysis

The smoke was written as though selecting an already completed command navigated directly to its
frozen result. The control contract intentionally requires a fresh Overseer decision for ordinary,
initial state-changing, completed state-changing, and terminal-transition commands. Browser and Go
tests cover that rule, but the packaged reset orchestration omitted the completed-command decision.

## Recommended Fix

1. Add a Player-probe marker after both Players receive the pending surface.
2. Make the native driver click the packaged Vue dialog's `ОДОБРИТЬ` button after that marker.
3. Continue only after both Players receive the frozen result, preserving every existing reset,
   convergence, navigation, and reopen assertion.
4. Rerun the smoke self-test and real packaged reset journey.
